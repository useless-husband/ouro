# ouro 導讀：給第一次讀編譯器程式碼的人

這份文件用白話說明 ouro 在做什麼、為什麼這樣做，讓你能在面試時把這個專案講清楚。不需要先讀過編譯器的書。

## 一、它解決什麼問題？

我們寫的 C 程式是給人看的文字。CPU 只看得懂一條一條的機器指令，例如「把兩個暫存器相加」「從記憶體某個位址讀 4 個位元組」。**編譯器**就是把前者翻譯成後者的程式。

ouro 是一個 C 編譯器，專門產生 Apple Silicon（M 系列晶片，arm64 架構）Mac 能執行的程式。它有三個值得一提的地方：

1. **能編譯自己（self-hosting）。** ouro 本身是用 C 寫的，所以 ouro 可以把自己的原始碼編譯成一個新的 ouro。這是編譯器界的「成年禮」：表示它支援的 C 夠完整，而且產生的程式碼夠正確，正確到能跑一個一萬多行、邏輯很複雜的程式。
2. **三階段結果完全相同。** 先用蘋果的 clang 編出 ouro（第 1 階段），用它編出第 2 階段，再用第 2 階段編出第 3 階段。第 2、3 階段的執行檔逐位元組相同（`make bootstrap` 會檢查並印出 SHA-256）。如果 ouro 有任何地方把自己編錯，第 2 階段的行為就會不一樣，第 3 階段通常就會跟著不同。
3. **不是玩具。** 它通過公開的 c-testsuite 全部 220 個測試，能編出 Lua 直譯器並通過 Lua 官方的測試套件，能編出 zlib（壓縮結果跟 clang 編的版本一模一樣），也能編出 26 萬行的 SQLite 資料庫，執行一組 SQL 的結果和 clang 版本完全相同。

## 二、八個關鍵概念（附生活比喻）

### 1. 流水線：一本書的翻譯分成很多道工序

編譯不是一步完成，而是一條流水線：

```
原始碼 → 詞法分析 → 前置處理 → 語法分析與型別檢查 → 中間表示 IR → 最佳化 → 指令選擇 → 暫存器配置 → 組合語言 → 組譯器 as → 連結器 ld
```

就像翻譯一本書：先把文字切成單字（詞法分析），處理縮寫與註腳（前置處理），理解句子結構與意思（語法與型別），寫成一份中立的筆記（IR），把筆記精簡（最佳化），最後再用目標語言寫出來（產生組合語言）。每道工序只做一件事，所以每一段都能單獨測試。

### 2. 巨集展開與「蓋章」：避免無限複印

C 的 `#define` 巨集就是「看到這個字就換成那段文字」。麻煩在於巨集可以引用自己，例如 `#define X X+1`，如果一直換下去就停不下來。ouro 用的是 Prosser 的 hideset 方法：每個展開出來的字都會被「蓋章」，記住它是從哪些巨集來的；蓋過某個巨集章的字，就不會再被那個巨集展開。好比影印店替每張影本蓋「已由某人影印」的章，看到自己的章就不再印一次。

### 3. 把「看不見的轉換」寫出來：像兌換外幣要開收據

C 有很多自動發生的型別轉換：`char` 會先變成 `int` 再相加，`int` 和 `unsigned` 比較時會變成無號……這些規則很容易出錯。ouro 在分析程式時，把每一個隱含轉換都變成語法樹裡一個明確的「轉型」節點，就像每次換匯都開一張收據。後面的階段只要照著收據做，不需要再懂 C 的轉換規則。

### 4. SSA 與 phi：每個值都有自己的版本號

在 SSA（靜態單一賦值）形式裡，每個變數只能被賦值一次。程式裡的 `s = s + a[i]` 會變成「s 的第 2 版 = s 的第 1 版 + …」。好比寫文件時每次修改都存成新版本，不覆蓋舊檔，這樣任何時候都知道某個值是從哪來的，最佳化就很好做。

那迴圈怎麼辦？迴圈開頭的 `s` 可能來自「第一次進迴圈的 0」或「上一圈算出來的值」。這時用一個 **phi** 節點表示「看你從哪條路走過來，就用哪個版本」，像是兩條路在路口會合時，看你從哪條路來，就拿那條路上的包裹。

### 5. 最佳化：提前算好、不重複算、把東西搬到迴圈外

- **常數傳播（SCCP）**：`int x = 3; int y = x * 4;` 編譯時就知道 y 是 12，不必等到執行。像考試時先把已知條件代進去算好。ouro 的 SCCP 也會發現「永遠不會走到的分支」並刪掉。
- **共同子運算式消除（CSE）**：同一個 `a * b` 算兩次，就只算一次。
- **迴圈不變量外提（LICM）**：迴圈裡每一圈都相同的計算，例如 `i * n`，搬到迴圈外先算好。像出門採買前先把清單寫好，而不是每到一個貨架就重寫一次。
- **死碼消除（DCE）**：算了但沒人用的結果直接丟掉，像清掉沒用到的草稿。
- **mem2reg**：把區域變數從「記憶體裡的格子」變成 SSA 的值，之後才有機會放進暫存器。

一個重要的原則：C 標準說「未定義」的運算（例如除以零），ouro 不會在編譯期替你算出一個答案，而是保留原樣。

### 6. 暫存器配置：只有 25 個抽屜的辦公桌

CPU 的暫存器像辦公桌上的抽屜，又快又少（ouro 可用的大約 25 個整數暫存器）；記憶體（堆疊）像倉庫，很大但比較慢。程式裡可能有幾千個值，必須決定誰放抽屜、誰放倉庫。

ouro 用**線性掃描**：把每個值「從什麼時候到什麼時候還需要」畫成時間軸上的區間，依時間順序分配抽屜。區間可以有「空洞」——某段時間這個值暫時用不到，抽屜就能先借給別人。抽屜不夠時，要把某個值搬去倉庫（spill），ouro 會選「搬走代價最小」的那個：用得少、又不在迴圈裡的值。這個改進讓 Lua 直譯器核心函式的倉庫存取從 3,056 次降到 327 次。

另一個限制是「函式呼叫會弄亂一部分抽屜」：呼叫別的函式時，有些暫存器可能被對方改掉（caller-saved），所以跨過呼叫還要用的值，只能放在對方保證會還原的抽屜（callee-saved，x19 到 x28）。

### 7. 呼叫慣例（ABI）：大家約好的交接方式

函式 A 呼叫函式 B 時，雙方要先約好：第 1 個參數放哪個暫存器？結構放不下怎麼辦？回傳值放哪？這套約定叫 ABI。ouro 編出的程式要能呼叫系統函式庫（例如 `printf`，由 Apple 用 clang 編譯），所以必須和 Apple 的約定一字不差。

Apple 的 arm64 約定和標準的 AAPCS64 有幾處「方言」差異：堆疊上的參數緊密排列（一個 `char` 只占 1 位元組）、可變參數（像 `printf` 的 `...`）一律放堆疊、`char` 是有號的、x18 暫存器保留不能用。ouro 用一個測試產生器檢查：自動產生上百種函式，讓 ouro 和 clang 編的程式互相呼叫，所有組合的結果都必須相同。我們也故意把一條規則改錯，確認測試真的會抓到。

### 8. 自我編譯：會印出自己零件的印刷機

想像一台印刷機能印出組成自己的零件，用這些零件組出第二台，第二台再印出第三台的零件。如果第二台和第三台完全一樣，就表示這台機器「穩定」：它印出的東西不會越印越走樣。ouro 的三階段自我編譯就是這個檢查。為了讓結果完全一樣，程式裡不能有任何依賴「記憶體位址大小」「雜湊表順序」或「當下時間」的地方，這在設計時就要很小心。

## 三、檔案導覽

| 檔案 | 做什麼 |
|---|---|
| `src/ouro.h` | 所有階段共用的資料結構與函式宣告，先讀這個 |
| `src/main.c` | 驅動程式：讀命令列選項、跑流水線、呼叫 `as` 和 `ld` |
| `src/util.c`、`src/diag.c` | 記憶體配置、字串、雜湊表；錯誤訊息的格式與插入符號 `^` |
| `src/lex.c` | 詞法分析：把文字切成 token，處理數字與字串常數 |
| `src/pp.c` | 前置處理器：`#include`、`#define`、`#if`、巨集展開 |
| `src/type.c` | 型別：大小、對齊、結構的欄位位置、型別轉換規則 |
| `src/parse.c` | 宣告與敘述的語法分析、名稱的作用域 |
| `src/expr.c` | 運算式的語法分析、型別檢查、常數摺疊 |
| `src/init.c` | 初始化器（`= {1, 2, .x = 3}`）與全域變數的資料內容 |
| `src/ir.c` | 中間表示的資料結構、印出（`--dump-ir`）與驗證器 |
| `src/irgen.c` | 把語法樹轉成 IR，並依 Apple 規則安排函式呼叫的參數 |
| `src/abi.c` | 判斷一個 C 型別在呼叫時要怎麼傳（整數暫存器、浮點暫存器、堆疊） |
| `src/cfg.c` | 控制流程圖整理、支配樹、迴圈深度 |
| `src/mem2reg.c`、`src/sccp.c`、`src/opt.c`、`src/licm.c` | 最佳化：轉 SSA、常數傳播、化簡、CSE、DCE、多餘載入消除、迴圈外提 |
| `src/isel.c` | 指令選擇：IR 變成 arm64 指令（暫存器還是虛擬的） |
| `src/regalloc.c` | 存活分析與線性掃描暫存器配置、堆疊框架的配置 |
| `src/emit.c` | 輸出組合語言：函式開頭結尾、溢出值的載回、全域資料 |
| `include/` | ouro 自己的 C 標準函式庫標頭檔 |
| `tests/` | 各層測試：unit、pp、diag、ir、asm、regress、abi、fuzz、bench |
| `scripts/` | 測試與量測腳本：bootstrap、c-testsuite、Lua、zlib、ABI、fuzz、benchmark |

建議閱讀順序：`ouro.h` → `main.c` 的 `compile_to_asm` → 挑一個小程式用 `--dump-ir` 和 `-S` 看輸出 → 對照 `irgen.c` 和 `isel.c`。

## 四、十個可能的面試問題

**1. 編譯器能編譯自己，為什麼重要？**
它證明編譯器支援的 C 夠完整，產生的程式也夠正確，能跑一個上萬行的真實程式。而第 2、3 階段逐位元組相同，證明輸出是穩定、可重現的。它還抓到 ouro 自己原始碼裡的一個未定義行為：處理 `switch` 時用 `for (x = lo; x <= hi; x++)` 列舉 case 值，當 `hi` 是 `LONG_MAX` 時 `x++` 會溢位。clang 編的版本剛好沒事，ouro 自己編的版本（整數溢位會繞回）卻當掉。所以現在第 2 階段的編譯器也要跑完整的測試（`make stage2-test`）。

**2. 什麼是 SSA？為什麼要用？**
每個值只被賦值一次，合流處用 phi 選擇來源。這讓「某個值從哪裡來」一目了然，常數傳播、CSE、死碼消除都變得簡單又快。

**3. 你的暫存器配置怎麼做？遇到過什麼問題？**
線性掃描：把每個值的存活範圍當成區間，依開始時間分配暫存器。第一版每個值只有一個大區間，又總是把「結束最晚」的值丟去堆疊，結果 Lua 直譯器裡有 295 個值被溢出。改成「有空洞的區間」，並依使用次數和迴圈深度選擇要溢出誰之後，降到 54 個。

**4. Apple 的 arm64 呼叫慣例和標準有什麼不同？你怎麼確定做對了？**
堆疊參數緊密排列、可變參數一律放堆疊、呼叫端負責延伸窄整數、`char` 有號、x18 保留。我先用 clang 編譯小程式觀察，再寫測試產生器：ouro 和 clang 的呼叫端與被呼叫端交叉組合，結果必須相同；故意改錯一條規則，測試會失敗。

**5. 怎麼知道編譯器沒有把程式編錯？**
多層測試：單元測試、和 `clang -E` 比對的前置處理測試、精確的錯誤訊息測試、檢查 IR 和組合語言的模式測試、和 clang 輸出比對的程式、隨機程式產生器、c-testsuite、Lua 與 zlib 的官方測試，以及三階段自我編譯。另外在測試時，每個最佳化階段之後都會跑 IR 驗證器。

**6. 隨機程式測試要怎麼避免「其實是程式本身有問題」的假警報？**
產生器只寫定義良好的程式：有號運算經過檢查溢位的輔助函式、位移量取餘數、除法先檢查。第一版還是出現假警報，原因是 C 沒規定運算式裡兩個函式呼叫的先後順序，而那兩個函式都會改同一個全域變數。後來改成只在敘述層級呼叫函式。還寫了一個縮小器，自動把出問題的程式縮小，並用 UBSan 確認沒有未定義行為。

**7. 舉一個你找到的真實 bug。**
在把 Lua 連同它的內部斷言一起編譯時，程式一啟動就斷言失敗。用「其他檔案都用 clang 編，一次只換一個檔案用 ouro 編」的方式找到兩個出問題的檔案，再看組合語言，發現分支指令被放在計算條件的指令「前面」，所以判斷的是舊的暫存器內容。這只在條件是常數位址時發生，例如 `assert(x && "訊息")`。修好後加了一個檢查：任何暫存器在被寫入前就被讀取，編譯器就直接報內部錯誤，之後又靠它抓到另一個 bug。

**8. 為什麼不用 Apple 的系統標頭檔？**
它們用了很多 clang 專屬的擴充（blocks、可用性屬性、符號別名）。實作這些和編譯 C 無關，所以 ouro 自帶 41 個小標頭檔，在影響二進位介面的地方（例如 `stdin` 的真實名稱、`errno` 的實作、`jmp_buf` 和 `struct stat` 的大小）照 Darwin 的定義寫。代價是遇到沒提供的宣告就要補。

**9. ouro 跟 clang 比起來表現如何？**
ouro -O1 產生的程式在每個測試程式上都比 clang -O0 快，大約是 clang -O2 速度的一半到持平。差距主要來自 ouro 沒做的最佳化：內聯、向量化、迴圈展開。編譯速度方面，ouro 把 Lua 編成組合語言比 clang -O0 快約 4 倍。數字是在共用的機器上量的，所以 README 有註明誤差。

**10. 如果再給你一個月，你會做什麼？**
直接輸出 Mach-O 目的檔（現在大部分建置時間花在執行系統組譯器）、加入函式內聯、做區間分割的暫存器配置，並支援多維的可變長度陣列與 `_Complex`。
